# Milestone A implementation report

Implemented on `feature/ta-milestone-a`, based on `4c721ca044e14724e544c28127326444d24810a4`. Milestones B and C are documented only.

## Behavior and schema

- Jobs: optional openings, employment type, nullable salary bounds, a same-tenant active hiring manager, structured screening criteria, close timestamp/reason. Existing payloads remain accepted.
- Assignments: admin-created/revoked job/user/role relationships. One access-policy service controls scoped visibility and decisions. Unassigned managers/interviewers receive 404 for individual resources and empty filtered lists. Existing recruiter/admin permissions remain.
- Stage events: append-only evidence, transactional with application creation, stage decisions, offer creation and hire. Existing rows are backfilled. Rejection requires a canonical reason code. History is available to the same roles that can read the application.
- Offers: decline, withdrawal, expiry and revisions; expiry date; configurable maker-checker. One active offer per application is enforced by a partial unique index.
- Lists: parameterized job/stage/status/date/text filters, whitelisted sort and additive total. Candidate combined filters match the same application. Existing data/pagination envelopes remain.
- Migration 004 adds job/offer columns, assignment and evidence tables, composite tenant foreign keys, indexes, forced RLS and exact runtime grants. Migration 005 is generated by the existing enum workflow. Original migrations 001–003 are unchanged. No runtime dependency was added.

## Decisions and limits

- Active means DRAFT, APPROVED or ACCEPTED; there is no new ACTIVE state. Accepted offers stay active and hireable after their expiry date. Declined/withdrawn/expired rows remain as history; their application stays in OFFER for a revision.
- Pending expiry is checked during approval/acceptance; `/expire` persists expiry manually and replacement creation expires due pending offers lazily. No background scheduler is introduced.
- Maker-checker defaults on in production and off in development/test to preserve existing development workflows; the explicit environment setting overrides either default.
- `hiringManagerUserId` is descriptive. It does not grant access without an explicit HIRING_MANAGER assignment. Assignment users must have the matching active global role; RECRUITER_OWNER maps to RECRUITER.
- Rejection reasons are QUALIFICATIONS, EXPERIENCE, COMPENSATION and OTHER. Historical rejected applications use OTHER and a migration note; their actor/from-stage are null because historical evidence is unavailable.
- Backfill temporarily removes FORCE RLS from applications inside the migration transaction so the owner can read historical rows, then restores FORCE before commit. Runtime is a separate non-owner role. A seeded upgrade test verified the backfill and restoration.
- Salary bounds are nullable numeric amounts; employment types are FULL_TIME, PART_TIME, CONTRACT and INTERN. No new job states are introduced.
- Text search uses ILIKE with SQL wildcard semantics. No extension is installed; leading-wildcard searches may scan tenant data. `status` means job status, including on application/candidate lists. Date bounds are inclusive ISO timestamps. Sort is created_at or updated_at with asc/desc.
- The route snapshot is intentionally updated for new endpoints and scoped-role grants. Existing routes/status codes are retained; rejection reason validation is the explicitly requested stricter workflow rule.
- No public intake, resume, retention, interview, report, AI, queue or real provider integration is implemented.
